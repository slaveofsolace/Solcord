- Public compatibility names/interfaces remain attributable to their owners and are not claimed as SoulCord marks.
- Vencord GPL source is not included. If later adaptation occurs, it must land in a clearly mapped GPL-3.0-or-later component with retained headers and notices; that is not part of V1.
- Catalog addon files acquired after an explicit setup **Apply and verify** remain separate third-party addons in the compatibility plugin directory with their own headers, authorship, and licenses. SoulCord does not relicense them or claim authorship.
- A candidate with no controlling license may only be acquired unchanged through its immutable official-catalog source. It may not be modified, copied into the SoulCord source tree, or described as SoulCord-authored.

The exact review scope is 323 metadata-ingested records, 47 plugin payloads fetched into sibling quarantine and statically screened, 36 requested plugin payloads manually dispositioned, and zero community candidates accepted for installation. Source/license review of the 114 catalog themes and the remaining plugin records is still pending. The five shipped SoulCord themes are original local assets and are reviewed separately from the BetterDiscord theme catalog.

The review stages are deliberately distinct:

1. `metadata: REVIEWED` means the catalog record was parsed and its source URL contains an immutable revision. It is not a source, license, or security verdict.
2. For the 47 screened plugin payloads only, `provenance: LICENSE_RECORDED` or `OFFICIAL_CATALOG_UNCHANGED_ONLY` identifies the handling boundary. Every other record remains provenance-pending.
3. For the 36 requested candidates, `securityDisposition` records the manual source decision and is bound to the exact catalog ID, immutable revision, and source SHA-256. Schema drift, duplicate reviewed records, or any binding mismatch aborts catalog generation. `SAFE_TO_RUNTIME_TEST` and `ACTION_GATED_TEST` permit isolated testing only; `HOLD` and `REJECT` cannot enter setup staging.
4. `runtime: PENDING` and `installable: false` prevent any claim that the aggressive preset is accepted. Runtime acceptance must bind the exact source/dependency hashes, SoulCord commit and artifact, Discord version, cleanup result, and human gate before this state can change.

Deep source-review results for the requested 36 are:

- `SAFE_TO_RUNTIME_TEST` (11): BetterFolders, CallTimeCounter, HideDisabledEmojis, ViewProfilePicture, DiscordEffects, PermissionsViewer, InsertTimestamps, ActivityFilter, VoiceActivity, DoubleClickToReply, and ShowSpectators.
- `ACTION_GATED_TEST` (4): FileNameRandomization, AudioOptions, InvisibleTyping, and NotifyWhenMuted.
- `HOLD` (19): BlurNSFW, VoiceMessages, PinDMs, MessagePeek, BetterSearchPage, ServerHider, PersonalPins, CompleteTimestamps, ReadAllNotificationsButton, ServerDetails, ImageUtilities, RevealAllSpoilers, BetterFriendList, BetterVolume, BetterAnimations, DoNotTrack, SpellCheck, SplitLargeMessages community mode, and CharCounter.
- `REJECT` (2): EditServers, because its user-supplied image request disables TLS certificate validation; Translator, because it stores provider credentials in ordinary settings, embeds provider credentials, supports bearer-auth and arbitrary endpoints, and patches composer-send behavior.

The accepted default built-in set is DoNotTrack, DoubleClickToReply, and InvisibleTyping; none stages the corresponding community files. Guarded SplitLargeMessages remains implemented as a SoulCord PREVIEW, but it is not recommended, transaction-executable, or enabled by setup until its disposable Discord modal/clipboard acceptance receipt exists. Its community mode and BDFDB remain held. Matching enabled owner plugins take precedence to avoid duplicate patches.

The transaction machinery can verify immutable bytes after a candidate earns runtime acceptance, but the current setup path requires both `stageable: true` and `installable: true`. Because every community candidate is currently `installable: false`, setup cannot download, stage, install, or enable any of them. A production rollout must not treat static-screening eligibility as enabled or proven.

## Acquisition controls

Both supplied ZIPs remain unchanged outside the repository and were copied into an isolated quarantine directory before extraction. Offline inventory checked traversal, collisions, symlinks, nested archives, encrypted entries, and active content. The delivery manifest and nested archive inventories were verified before any source comparison. Original bundles, third-party payloads, catalog response bodies, and quarantined toolchains are not committed.

The setup transaction accepts only immutable `raw.githubusercontent.com` URLs containing a 40-character revision, rejects redirects, enforces a 5 MiB per-file ceiling, verifies SHA-256 before apply, and refuses to overwrite a differing local file. This is acquisition-policy evidence only; integration, cleanup, UI, and live-account behavior still require runtime review.
